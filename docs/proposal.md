# flower_pow 自主生成 POC 需求说明（proposal）

> 范围：为 flower_pow 增加「把已确认的发现沉淀成可复用 POC 规则」的能力。
> 本轮只定义**做什么**，技术方案见 `design.md`（Phase 3），任务拆分见 `tasks.md`（Phase 5）。

## 1. 项目背景

flower_pow 是 AI Agent 驱动的 Web 漏洞扫描器，检测能力由 `poc/*.yaml` 里的**声明式规则**驱动，目前 33 条，覆盖常见 CVE 探针、敏感路径、鉴权缺失、信息泄露。扫描链路是「指纹 → RAG 召回规则 → LLM 重排 → 只跑值得跑的规则」。

问题在于这条链路是**单向**的：规则是人先写好、库先建好，扫描才有东西可召回。真实目标上遇见的形态（某框架特有的错误页、某后台特有的越权路径、某 SDK 特有的调试接口）往往不在库里，只能靠 Agent 当场手工请求验证一次，报告写完就结束了。下一次遇到同类目标，同样的手工过程要重来一遍——经验没有沉淀成能力。

本需求要补的就是这一段回程：**把一次已经确认的发现，固化成一条符合现有结构的规则，经校验与验证后进入生产库，下次同类目标能被自动召回和执行。**

## 2. 要解决的问题

1. **零沉淀**：一次手工确认的漏洞，除了写进当次报告，对后续扫描没有任何增量价值。
2. **库不可写**：当前文件操作被限制在产物目录内，规则目录对 Agent 完全不可达，连"想沉淀"的通道都没有。
3. **无准入标准**：即使能写，也没有任何机制判断"这条规则对不对"——匹配过宽会变成全站误报源，匹配过窄等于没写，ID 撞车会覆盖已有规则。
4. **不可追溯**：现有一条规则背后"为什么这么写、在哪个目标上验证过"无从查证，出问题无法定位、无法回滚。

## 3. 目标用户

单人安全测试者（本工具作者）在两类场景下使用：

- **日常渗透**：扫到一半发现库里没有的漏洞形态，顺手沉淀，下次同类目标自动覆盖。
- **回归沉淀**：一次项目测完，把项目中确认过的、有共性的发现整理进库，形成自己的私有规则集。

## 4. 核心目标

- 从「已确认的发现证据」到「可被扫描链路自动召回并执行的规则」全程可在工具内完成，不手写 YAML、不手工改目录。
- 进入生产库的规则**必须验证过**：既能在历史响应上复现命中，也能在当前目标上实跑命中。
- 任何一条生成的规则都可追溯来源、可一键回滚。

## 5. MVP 功能范围

按可验证的功能条目列出，编号供 design/tasks 反向对照。

| 编号 | 功能 | 一句话说明 |
|---|---|---|
| R1 | 草稿生成 | 依据"目标指纹 + 一次已确认的发现证据"，生成一条结构完整的规则草稿，写入 `create_code/` 草稿区，附带来源元数据 |
| R2 | 静态校验 | 检查字段完整、匹配表达式可编译、匹配条件非空、必须带反向断言、ID 全局不重复（与生产库、草稿区都不撞） |
| R3 | 离线回放验证 | 用本地产物目录里已保存的历史响应回放，验证"该命中的命中、不该命中的不命中" |
| R4 | 在线实跑验证 | 在当前会话目标上真实请求一次，只有确认命中才算通过 |
| R5 | 晋级 | 验证通过的草稿移入 `poc/` 生产库，并让其在后续检索中可被召回（无需重启进程） |
| R6 | 双入口 | 终端命令与 Agent 工具各提供一个入口：生成草稿、查看草稿状态、晋级、回滚 |
| R7 | 审计与回滚 | 每条草稿/规则记录来源（哪次会话、哪条证据、什么模型判断）、验证结论与时间；可一条命令退回草稿区 |

## 6. 用户操作流程

**流程 A：人工触发**

1. 扫描或对话中确认了一个发现（有请求、响应、能证明漏洞的特征）。
2. 敲命令要求沉淀该发现，指定或由系统推断类别、等级。
3. 系统生成草稿并展示：规则内容、校验结果、回放结果、实跑结果。
4. 用户阅读后决定：晋级 / 继续修改 / 放弃。
5. 晋级后，该规则立即参与后续召回。

**流程 B：模型自主触发**

1. Agent 在会话中判定"这是现有库里没有的形态"，且手上证据充足。
2. Agent 调用工具生成草稿，工具返回校验/回放结论（以及失败原因）。
3. **写生产库仍需用户确认**——模型可以起草，不能自行入生产库。
4. 用户确认后晋级，结论回写会话。

## 7. 输入和输出

**输入**

- 目标信息：URL、命中的接口、技术指纹（语言/框架/组件/版本）。
- 证据：原始请求（方法、路径、头、参数/载荷）与原始响应（状态、头、正文片段）。
- 判断：漏洞类别、危害等级、一句话描述与修复建议（可由模型从证据推断，也可由用户指定）。

**输出**

- 草稿区：`create_code/` 下一条规则文件 + 一份来源元数据（会话 ID、证据引用、生成时间、模型与提示版本）。
- 校验报告：通过/不通过，以及逐条失败原因（哪一条规则、哪一行、为什么）。
- 验证结论：回放命中情况、实跑命中情况、失败时的原始证据。
- 生产库：`poc/` 下最终规则文件（与现有 33 条同构）。
- 审计台账：一条记录，可被列表命令查询。

## 8. 异常场景

| 场景 | 行为 |
|---|---|
| 只有猜测没有证据（无请求/无响应） | 拒绝生成，提示先取证 |
| 证据不足判断类别 | 生成最宽泛类别的草稿，并标注"待人工归类" |
| ID 与生产库或草稿区重复 | 自动追加序号并提示；不得静默覆盖 |
| 回放样本缺失（本地无对应历史响应） | 跳过回放，标记"仅在线验证"，不因此判失败 |
| 实跑未命中 | 草稿保留在草稿区并记录失败原因，**禁止晋级** |
| 目标不可达 / 超时 / 被 WAF 拦 | 不判失败，标记"待重试"，允许稍后补验 |
| 校验不通过（空匹配、坏正则、缺反向断言） | 拒绝保存为可晋级草稿，返回逐条原因 |
| 只读模式开启 | 生成与静态校验可用；实跑若涉及写操作一律拦截 |
| 模型不可用（无 Key / 调用失败） | 生成入口不可用，但校验、晋级、回滚、列表仍可用 |
| 晋级后规则导致大量误报 | 可一键回滚到草稿区，生产库恢复原状 |

## 9. 非功能需求

- **准入不可绕过**：任何路径（命令或工具）都不得把未验证的草稿直接写入生产库。
- **零新增第三方依赖**：复用现有 HTTP 客户端、YAML 解析与自实现的向量检索。
- **成本上限**：单条草稿生成的模型调用不超过 1 次；校验与回放不得联网。
- **执行兼容**：生成的规则必须能被现有加载器与检测器直接执行，不改执行引擎。
- **可读性**：生成的规则须带中文说明与修复建议，与现有 33 条风格一致。
- **安全**：生成的规则不得包含目标凭据原文；证据中的敏感字段按现有脱敏规则处理。
- **性能**：校验 + 回放单条耗时应在秒级，不阻塞交互。
- **进程可用性**：晋级后无需重启进程即可检索到新规则。

## 10. 明确不做的事情

- 不生成脚本型 / 代码型检测器，只做声明式规则。
- 不做漏洞的自动发现与自动利用（只沉淀已确认的发现，不主动挖洞）。
- 不做规则的自动评分、自动淘汰（后续单独评估）。
- 不改现有检测器执行引擎，不动现有 33 条规则。
- 不做规则共享、上传、市场、云端同步。
- 不做多用户与权限体系。
- 不自动提交 git。
- 不生成针对特定目标的、不可复用的"一次性脚本"。

## 11. 验收标准

| 编号 | 验收项 | 操作步骤 | 预期结果 |
|---|---|---|---|
| A1 | 能生成 | 对一次带完整请求/响应的发现执行生成入口 | `create_code/` 下出现规则文件与元数据，现有加载器可解析该文件 |
| A2 | 能拦坏规则 | 手工把草稿的匹配条件清空、或写入非法正则后重新校验 | 校验不通过，逐条给出原因，草稿不允许晋级 |
| A3 | 能防撞车 | 用与 `poc/` 中已有 ID 相同的草稿执行校验 | 被拒绝或自动改名，且生产库原文件未被修改 |
| A4 | 回放有效 | 用本地产物目录中的历史响应执行回放 | 报告的命中/未命中与规则实际语义一致，无联网行为 |
| A5 | 实跑有效 | 对一个可命中的目标执行在线验证 | 命中并记录原始证据；未命中时禁止晋级 |
| A6 | 晋级生效 | 晋级一条验证通过的草稿 | `poc/` 下出现该文件，草稿区移除，列表命令可见，后续检索可召回 |
| A7 | 可回滚 | 对已晋级的规则执行回滚 | `poc/` 下该文件消失、草稿区恢复，检索不再召回 |
| A8 | 审计可查 | 查询审计台账 | 每条记录含来源会话、证据引用、验证结论、时间 |
| A9 | 双入口一致 | 分别用终端命令与 Agent 工具走一遍同一流程 | 两者遇到同一违规输入时给出同一结论，生产库行为一致 |
| A10 | 无回归 | 跑现有三道门禁 | 编译、密钥扫描、全量回归全部通过，无新增第三方依赖 |
