# flower_pow

**AI Agent 驱动的 Web 漏洞扫描器** —— 说人话 → 模型调用本机工具拿真实证据 → 研判 → 报告

> ⚠️ 仅用于**已获得书面授权**的目标。默认只读（`readonly: true`）。

📄 想看每个文件干什么、里面每个模块点负责什么 → [`doc/auxiliary/FILE_MAP.md`](doc/auxiliary/FILE_MAP.md)

## 1. 它和普通扫描器的区别

市面上的扫描器要么太重（商业引擎吃 license）、要么太糙（裸 HTTP 拼手写规则，误报满天飞）。
  
这个项目的做法是**让规则只负责"确定性的事"，把需要判断的事交给检索和模型**：

| 环节           | 谁来决定                   | 为什么这么分                         |
| ------------ | ---------------------- | ------------------------------ |
| 跑哪些 POC      | **RAG 检索 + LLM 重排**    | 全库盲扫会把请求量放大一个数量级，而命中率为零        |
| 怎么发请求、怎么匹配   | **规则**（YAML 声明式）       | 这部分必须确定、可复现、可审计                |
| 这一轮做什么、调哪个工具 | **AI Agent**（默认）/ 固定剧本 | 模型看着当前状态决定打法，而不是照剧本走完四阶段       |
| 哪些命中是真漏洞     | **LLM + 真实 HTTP 证据**   | 软 404 / 统一错误页 / WAF 拦截页只能靠语义判断 |
| 风险排序依据       | **外部 CVE 情报**          | CVSS / KEV / EPSS 是客观指标，优于手写等级 |

一句话：**规则管"确定性"，RAG 管"相关性"，Agent 管"下一步做什么"，LLM 管"判断力"。**

## 2. 快速开始

```bash
cd D:/anyworkspace/python/flower_pow

# 1) 安装（依赖刻意保持最小）
.venv/Scripts/pip install -r requirements.txt

# 2) 直接运行：自动体检环境 → 索要 API Key → 进入 AI Agent 会话
.venv/Scripts/python.exe flower_pow.py

# 3) 想启用 LLM 重排与降误判，填入 API Key（首次运行会交互询问并写入 .env，
#    也可先 export DEEPSEEK_API_KEY=sk-xxx）
export DEEPSEEK_API_KEY=sk-xxx

# 4) 检查引擎、采集器、索引、外部工具状态
.venv/Scripts/python.exe flower_pow.py engines
.venv/Scripts/python.exe flower_pow.py tools      # Agent 能调用的两层能力

# 5) 一次性扫描（不开对话）
.venv/Scripts/python.exe flower_pow.py scan http://你的目标
```

首次运行会做一次完整体检并打印：外部工具探测、本机能力清单、POC 库与索引状态、
  
自定义工具清单、POC 索引、API Key 来源，然后进入对话。**体检在前、要 Key 在后**——扫描、RAG、报告
  
链路不依赖大模型也能跑，不能让用户误以为"没 Key 就没法用"。

密钥落在 `.env`（已在 `.gitignore` 中），**不写 `config.yaml`**：配置文件通常是要提交
  
进仓库的，Key 放进去迟早会被 commit 出去一次。

### 2.1 排障：搬过目录之后

Windows 的 venv **不可迁移**。项目目录改名或搬移后，`python.exe` 仍能用
（靠相对定位找 site-packages），但 `.venv/Scripts/` 下的 **exe 启动器全部失效**——
它们的绝对路径在创建时就烧进了 PE 头：

```bash
# 典型症状
Fatal error in launcher: Unable to create process using '"D:\旧路径\.venv\Scripts\python.exe" ...'
```

排查（Git Bash 用 `strings`）：

```bash
strings .venv/Scripts/*.exe | grep -i 旧目录名
```

修复——用还活着的 `python -m pip` 强制重装，让 pip 按当前路径重新生成启动器，
**不必重建 venv、已装包全部保留**：

```bash
.venv/Scripts/python.exe -m pip install --force-reinstall --no-deps \
    pip typer httpx idna markdown-it-py Pygments pytest
```

> 关键点：`python -m pip` 走 `sys.path` 相对定位，所以启动器全坏时它往往是**唯一还能用的入口**。

### 2.2 排障：`ModuleNotFoundError: No module named 'typer'`

```powershell
PS> py .\flower_pow.py
ModuleNotFoundError: No module named 'typer'
```

这**不是依赖没装**，而是**跑在了错误的解释器上**。Windows 的 `py` 启动器（`C:\Windows\py.exe`）有两个坑：

**坑一：`py` 无视已激活的虚拟环境。** 激活 venv 只改 `PATH`，而 `py` 不查 `PATH` 里的 venv，
直接用 `py.ini` / `PY_PYTHON` 指定的解释器。验证：

```powershell
python -c "import sys; print(sys.prefix)"   # .venv 目录  ✅
py -c "import sys; print(sys.prefix)"       # D:\python    ❌ 不是 venv
py -0p                                        # 看 py 眼里有哪些 Python
```

所以 `pip install typer` 装进了 `D:\python\Lib\site-packages`，对 venv 毫无作用。

**坑二：脚本首行的 shebang 会让 `py` 彻底绕过自己。** 若 `flower_pow.py` 首行是
`#!/usr/bin/env python3`，`py` 会按 shebang 去找 `python3` 这个名字，命中 `PATH` 里的**其它** Python
（如托管的 3.13），那个环境往往什么都没装。此时连 `py -c "import typer"` 都是好的，
只有 `py flower_pow.py` 失败——因为前者由 `py` 亲自执行，后者按 shebang 另起进程。

诊断方法（一眼看出跑歪了没）：

```bash
python -c "import sys; print(sys.executable)"
```

**根治（本项目已采用）**：首行**不要** shebang。入口文件是给人 `python xxx.py` 调的，
不需要可执行位；去掉后 `py` / `python` 行为一致。

**正确的启动方式**，按优先级：

```bash
python flower_pow.py engines                  # venv 已激活时（推荐）
.venv/Scripts/python.exe flower_pow.py engines # 不确定激活状态时最稳
python -m flower_pow engines                  # 不想依赖 cwd
```

> 记不住就用第二条——完整路径永远指向对的解释器，不受 `PATH`、`py.ini`、shebang 任何影响。

若重装 pip 时出现 `WARNING: Ignoring invalid distribution ~ip`：`~` 前缀是 pip 的
「待删除」标记，说明上一版 pip 的目录卸载时被跳过残留了。确认现役版本后直接删掉
`site-packages/~ip` 与 `site-packages/~ip-*.dist-info` 即可。

**共 18 个命令**。`exploit --upload` 的闸门是人工审核通道，与 `readonly` 无关：
每次上传前都会在终端逐条确认，非交互环境下（没有确认通道）一个上传请求都不会发。

全局选项：`--classic` 跳过 Agent 走剧本、`--api-key` 直接传 Key、
  
`--save-key/--no-save-key` 控制是否写入 `.env`、`--no-probe` 跳过外部工具版本探测（更快）。

### 3.1 AI Agent 会话（默认形态）

直接说人话，模型会**自己决定调哪个工具**：

```
› 目标 http://127.0.0.1:8899 ，先做信息收集
  ⚙ set_target(url=http://127.0.0.1:8899)
  ⚙ recon_fingerprint(url=http://127.0.0.1:8899)
  ⚙ recon_openapi(url=http://127.0.0.1:8899)
  ⚙ recon_js(url=http://127.0.0.1:8899)
  ⚙ http_request(url=http://127.0.0.1:8899/actuator/env)
  …模型基于真实响应继续判断，最后给出结论与下一步建议
```

启动后**直接进提示符，不做开场白**。早期版本会让模型先自报家门（"我是渗透测试
操作员……请告诉我这次要测哪个目标"），但那段每次措辞都不同、在用户还没说话时
就刷屏一大段，既不提供用户没要求的信息，还白烧一轮 token。需要时用
`--kickoff` 或会话内 `/kickoff` 触发。

**Agent 与固定剧本的分工**：

|    | 固定剧本（`--classic`）       | AI Agent（默认）           |
| -- | ----------------------- | ---------------------- |
| 打法 | 第 1 轮必做信息收集，第 3 轮必做鉴权探测 | 模型看着当前状态决定             |
| 优点 | 稳定、可复现、不依赖模型            | 不会因为"这站根本没有登录接口"就死板推进  |
| 代价 | 会做无用功                   | 需要模型靠谱，故设了三道闸门（见 §4.1） |

会话内命令（两种模式通用）：

```
/agent [on|off]  切换 Agent / 剧本模式        /target [URL]  设定或查看目标
/tools           列出本机可调用工具            /key           重新设置 API Key（写入 .env）
/status          状态概概                      /assets [类型] 资产清单
/findings [等级] 发现列表                      /reset         **彻底重置**（销毁目标/资产/发现/凭证/对话历史/盘上快照）
/model           业务模型                      /report [格式] 导出报告
/resume [id]     载入会话（不带 id 取最近一次，连对话历史一起恢复）
/backfill        从会话历史回填发现的原始报文（老报告只有请求没响应时用）
/phase 名称      剧本模式切阶段（recon|model|exploit|iterate）
/next / /run     剧本模式推进阶段 / 当前阶段再跑一轮
/sessions        列出可恢复的会话
/clean           删掉空会话（没目标、没对话、没结果的那种）
/kickoff         让模型自我介绍一轮（启动时默认不说）
/auto            一键全自动：出警告 → 确认 → 跑完整条流水线并导出报告
Alt+Shift        同上（输入框里按下即触发，不必敲命令）
/quit            退出（自动保存；**空会话不保存**）
```

**换目标会清空一切**：`/target` 设成**与当前不同**的目标时，上一目标的资产、
发现、凭证、对话历史与 runner 运行期缓存会被整体清空——报告串线的根源大多
在这里。同一目标重复设定不动数据。

**`/reset` 是"砸了换把新的"**：不管当前处于什么状态，一律丢弃旧 `Session`、
换一把全新的空会话、删掉盘上快照。换句话说它不做"清对话历史、保留资产"这种
半吊子——要清就清干净。

**行编辑**：`←/→` 在已输入内容里移动光标、`Home/End`、`Delete`、
`Ctrl+←/→` 按词跳、`Ctrl+A/E` 行首行尾、`Ctrl+U/K` 清空/删到行尾、
`↑/↓` 翻历史、`Tab` 补全。终端表现异常时设 `FLOWER_POW_PLAIN_INPUT=1` 退回原生 `input()`。

**输入超过一行也正常**：按显示列宽（中文算 2 列）自己折行，用 ANSI 精确定位光标、
一次擦净所有折行，方向键上下跨行移动、`Home/End` 回到逻辑行首行尾。

状态落在 `data/sessions/<id>/session.json`，随时 `--resume` 断点续跑。
  
**凭证与 token 不写入快照**（快照可能被分享），恢复后需重新取得凭证
（Agent 模式下用 `login` 工具）。

#### 会话恢复：连对话历史一起恢复

快照里存了两类东西，**恢复时都会回来**：

| 存了什么 | 恢复后的效果 |
|----------|-------------|
| 资产、发现、业务模型、阶段、轮次记录 | `/assets`、`/findings` 立刻有东西可看 |
| **Agent 对话历史**（`history` 字段） | **模型记得上次聊过什么**，不重复劳动 |

第二项是关键。没有它，「恢复」只是恢复资产清单——模型看得到有哪些接口，
却不知道用户的测试意图和**已经排除过的方向**，于是把上次做完的事又做一遍。

```bash
python flower_pow.py chat --resume      # 启动时恢复最近一次
/sessions                # 会话内先看有哪些（按最后更新时间倒序）
/resume 20261011_测 aigc 接口越权          # 精确载入某一个（Tab 可补全）
```

#### 会话名 = 日期 + **第一轮**对话标题

```
data/sessions/
  20261011_测 aigc 接口越权与 OSS 写权限/session.json
  20261010_juice-shop 全量回归/session.json
```

早期目录名是纯 `int(time.time())`，`/sessions` 与 `/resume <Tab>` 列出来全是
`1789...`——**恢复的时候根本认不出哪次是哪次**。现在按「第一轮对话的标题」命名：

- 取**第一轮**而不是最后一轮：第一句才是"这次要测什么"，最后一轮往往是"出报告"。
- 日期在前 → 字典序 == 时间序，`ls` 出来天然有序。
- 标题里的 `<>:"/\|?*` 会清洗、超长会截断（否则 Windows 上写不出文件）。
- **目录名一经确定就不再改**（追加对话、`/title` 改名都不动目录），
  否则旧路径立刻失效、`--resume` 找不到自己刚存的会话。
- 旧的纯数字目录仍可加载，不会被新规则排除。

恢复后**不会**让模型自我介绍（`kickoff` 默认关，且恢复会话时强制跳过）——历史已回填，
再寒暄一遍既答非所问又多烧一轮 token。

#### 空会话会自动清理

"进来看看就又退出去"会留下一个**空快照**：没设目标、没说一句话、没拿到任何资产。
它的价值为 0，但会在 `/sessions` 里占位、在 `/resume <Tab>` 里参与补全，
还会把真正有用的那次挤出"最近 N 条"。三层处理：

| 时机 | 行为 |
|------|------|
| **退出时** | 判定为空则**不落盘**（`Session.is_empty`），磁盘上不留目录 |
| **恢复时** | `--resume` / `/resume` 先顺手清扫历史遗留的空壳，报一句汇总 |
| **手工清** | 会话内 `/clean`，或命令行 `python flower_pow.py sessions --clean` |

点名恢复一个空会话时（旧版遗留的），会**直接删掉并说明**，而不是载入一个空状态
让你以为快照坏了：

```
> /resume 1791665980
会话 1791665980 是空会话（没目标、没对话、没结果），已删除。
   用 /sessions 看可恢复列表，或直接开始新的一次测试。
```

判空**从严**——任一项有内容就保留：设过目标、说过话、**登录过**（`credentials`）、
推过阶段、有资产/发现/笔记，都算数。误删不可逆，"多留一个空壳"只是难看。
历史里只有 `system` 开场白（模型自己说的）**不算数**。

落盘前对 `history` 统一脱敏（`core/session/redact.py: redact_messages`）：对话历史里
往往混着工具返回的原始响应，直接存等于把 Cookie / Token 写进可能被分享的快照。
脱敏只在**写盘时**做，内存里的历史保持原值，否则 Agent 会拿着 `***` 去干活。
凭证与 token 仍然不落盘，恢复后需重新取得凭证（Agent 模式下用 `login` 工具）。

### 3.1.1 报告里的 POC 执行过程

交付报告要能被对方**复现**，光有「某接口有 SQL 注入」是不够的——得给出
打了什么、预期看到什么、实际看到了什么。每条发现现在都带这四栏：

| 字段 | 内容 |
|------|------|
| **触发 POC** | POC id 与名称（手工登记的标 `manual_` 前缀） |
| **发送请求** | **实际发出的 payload**，GET 的 query、POST 的 body、参数名、关键 header |
| **预期返回** | 把 YAML 的 `match` 规则翻成人话，如「响应体 包含 [SQLite/version]」 |
| **实际命中** | 真正触发的那条规则 + 响应片段 |

```
- 触发 POC：`manual_sqli_1512`（手工验证：SQL 注入（取版本号））
- 发送请求：`GET /rest/products/search?q=test')) UNION SELECT sqlite_version(),2,3--`
- 预期返回：响应 data[0].id 回显 SQLite版本号 3.44.2
- 实际命中：{"status":"success","data":[{"id":"3.44.2","name":"2"}]}
```

手工验证的漏洞没有 POC 定义可循，所以 `record_finding` 把 `payload` 也设成
**必填**——它是对方复现的唯一依据。探针发现则由 `detectors/base.py`
在 `send_request()` 时自动填充（`_payload_of` / `_expect_of`）。

### 3.2 Tab 补全与对话索引

#### Tab 补全（`core/completer/`）

命令名与**各命令的参数**都能补全——`/report m<Tab>` 直接补成 `/report md`。

| 键 | 行为 |
|----|------|
| `Tab` | 补全当前前缀；有唯一候选直接补齐 |
| `Tab` × 2 | 展示全部候选（不改动已输入内容） |
| `↑` / `↓` | 翻历史，同方向连续按会累积前缀（与 shell 一致） |

参数候选是**动态**的：

| 命令 | 候选来源 |
|------|----------|
| `/resume <Tab>` | 实际扫描 `data/sessions/` 得到会话 id |
| `/title <Tab>` | 当前已有的对话编号 |
| `/assets <Tab>` | 资产类型（port/path/api/endpoint/…） |
| `/target <Tab>` | 当前目标及其常见路径 |

**为什么自己实现**：`readline` 是 POSIX 模块，**Windows 官方 Python 发行版不提供**
（CPython 在 win32 下不编译它）。`pyreadline3` 要额外装，tkinter 在精简版里
也没编。本项目要求「只靠 httpx + yaml 就能跑」，所以自实现：Windows 用
`msvcrt.getwch()` 逐键读，POSIX 用 `termios` 切cbreak 模式。

**关键约束**：非 TTY（`echo "/help" | python flower_pow.py`、CI、脚本调用）
时自动退回原生 `input()`，**行为与原来完全一致**——补全绝不能拖垮程序。

**输入区怎么重绘**：`\r` 只回到**当前物理行**行首，输入一旦超过终端宽度就会
自动折行，这时 `\r` 回不到逻辑行首，按一行宽度清屏也擦不干净。所以自己按显示
列宽折行（CJK 按 2 列算），用 ANSI **相对**上移回到输入区首行、`\x1b[J` 一次
擦到屏幕末尾，再相对移回光标该在的位置。光标行号由上一次重绘返回、下次传回，
这样**回删**（行号变小）时也能正确上移。

> **全程不许用绝对定位**（`\x1b[行;列H`）。算出来的行列是"相对输入区首行"的，
> 拿去当屏幕绝对坐标用，光标会被扔到屏幕左上角，下一次重绘就从那里开始擦屏——
> 表现就是输入时整个屏幕乱跳、上方已打印的输出被抹掉。

Windows 控制台需要先开 `ENABLE_VIRTUAL_TERMINAL_PROCESSING` 才认这些序列；
拿不到控制台时退回单行重绘，并把内容**裁进一行**——不裁的话每次重画都会折行，
输入区会每敲一个字往下掉一行（实测 25 个字符掉 6 行）。

回归测试用**终端模拟器**验证屏幕结果（`scripts/_terminal_sim.py` 的假屏幕 +
`scripts/completer_terminal_test.py`）：
造一块假屏幕，按真实语义折行、上滚、处理转义序列，然后断言"输入区相对位置恒定、
上方内容不被动、下方无残留、全程没有绝对定位"。三个手感用例已固化：**超宽长输入**、
**折行后退格回短输入**、**Tab 弹候选后继续打字**。

这三条先用内部函数（`_repaint` / `_show_candidates`）验一遍，再**用真实按键循环
跑一遍**——用假的 `msvcrt` 喂键序列（`/re` + `Tab` + `Tab` + `port` + 回车），
从 `PromptReader.read()` 进去。为什么要两遍：只调内部函数只能证明"重绘函数对"，
证明不了**键盘分发**对——Tab 那一段（第一次只记候选、第二次才展示）就写在
`_read_win` 里，绕过它等于没测。

> 只对转义字符串做断言是自证的——算错行号照样"通过"（旧用例断言的 `\x1b[2;13H`
> 正是那个 bug 的产物）。所以断言必须落在屏幕结果上。
> 这些用例做过"种回 bug"验证：把绝对定位、`cur_row` 用新行号这两处分别改回去，
> 用例都会失败（后者表现正是输入区首行序列 `3→4→5→6` 向下漂移，按键循环那条
> 也一样报出来）。

#### 对话索引：每轮对话一个标题

恢复会话后想看「上次聊到哪了」，光有 39 条原始消息是不够的。所以每轮对话
都会生成一个 ≤20 字的中文标题：

```
/chats                查看对话索引（标题 + 用到的工具 + 时间）
/title 3 SQL注入验证   手工改某轮标题
```

标题优先用**小模型**总结（更准），失败则退回「取用户输入前 20 字」——
标题是索引不是交付物，不额外占深度模型。标题落盘前走
`redact()` 脱敏，与对话历史同一套规则。

### 3.3 剧本模式的四阶段（`--classic`）

`scan` 是一次性跑完就结束；剧本模式是**多轮**的，每一轮都真的发请求去测。
  
`/next` 或回车推进阶段，`/phase` 直接切换：

| 轮次 | 阶段   | 做什么                                         |
| -- | ---- | ------------------------------------------- |
| 1  | 信息收集 | 指纹、端口、JS、**接口文档**（OpenAPI/Swagger 全部操作转成资产） |
| 2  | 业务建模 | 推导资源/权限域/业务流，并**真的登录走一遍核心流程**               |
| 3  | 渗透测试 | 未授权访问、IDOR/越权、敏感字段出网、常规 Web 检测              |
| 4+ | 迭代深挖 | 扩大到全部接口复测、换角色交叉对比                           |

## 4. 工作原理

```
   目标 URL
      │
   ┌─────────────────────────────────────┐
   │ ② 侦察（collectors/）               │  指纹 → RAG 的 query 来源
   │   port_scan   TCP 端口探测          │  端口 → 资产
   │   js_analyze  JS 静态分析（只读）    │  端点/密钥/内网地址 → 资产
   │   path_scan   字典爆破（可选）      │  路径 → 资产
   └──────────────┬──────────────────────┘
                  ▼ 指纹 + 资产
   ┌─────────────────────────────────────┐
   │ ③ RAG 召回（kb/）                   │  混合检索：0.35×余弦 + 0.65×BM25
   │   indexer    纯 Python 向量库      │  + 技术栈不匹配降权
   │   retriever  召回 + LLM 重排        │  + 基线 POC 并入
   │   intel      CVE 情报增强           │  CVSS / KEV / EPSS
   └──────────────┬──────────────────────┘
                  ▼ 值得跑的 POC 清单
   ┌─────────────────────────────────────┐
   │ ④ 验证（detectors/）                │  软 404 抑制 + 证据留存
   │   http_detector  声明式规则求值     │
   └──────────────┬──────────────────────┘
                  ▼ 带 Evidence 的发现
   ┌─────────────────────────────────────┐
   │ ⑤ LLM 降误报（llm/）                │  只依据证据判真伪，禁止推测
   └──────────────┬──────────────────────┘
                  ▼
        JSON + Markdown + HTML + 原始报文
```

**顺序不能换的两个硬约束：**

- **侦察必须在检索之前** —— RAG 的召回质量完全取决于指纹质量。只拿 "HTTP 200"
    
  去检索，等于盲猜。
- **研判必须在验证之后** —— 没有证据就没有研判的输入。让模型"看漏洞名判断真伪"
    
  必然产生幻觉。

### 4.1 Agent 循环：对话怎么变成动手

上面是 `scan`/`--classic` 的固定流水线。默认形态是 `chat`的 Agent 循环，
  
它把"人说一句话"翻译成"一串真实工具调用"：

```
   用户一句话
      │
      ▼
┌─────────────────────────────────────────┐
│ system 提示词（每轮重建）               │
│   当前会话状态 + 只读开关               │
│   + 可用工具清单（含外部工具真实清单）  │
└────────────┬────────────────────────────┘
             ▼
   ┌──────────────────────────────────┐
   │ 模型流式输出（stream_chat）       │
   │   → 文本     ：边说边打字         │
   │   → tool_calls：调哪个工具、传什么参│
   └────────┬─────────────────────────┘
            │本地执行（core/tools/runner/）
            ▼
   ┌──────────────────────────────────┐
   │ 参数白名单 → 只读拦截 → 无 shell  │
   │ → 执行 → 结果文本回灌给模型       │
   └────────┬─────────────────────────┘
            └──► 模型基于**真实结果**继续判断…（回到上一步）
            │
            ▼  模型不再要求调工具
        文字结论交还用户（资产/发现已落会话）
```

**三道安全闸门**（`core/tools/runner/base.py`，模型不可绕过）：

| 闸门      | 做什么                                     | 为什么必须有                   |
| ------- | --------------------------------------- | ------------------------ |
| 参数白名单   | 外部工具的选项、文件路径逐项校验                        | 模型给的参数可能带 `--output` 写文件 |
| 只读拦截    | `intrusive` 工具（sqlmap/nikto/hydra…）直接拒绝 | 攻击性工具会改业务数据              |
| 无 shell | `subprocess` 一律传 argv 数组、`shell=False`  | 没有 shell 就没有重定向、管道、命令替换  |

另有两道与白名单无关的兜底：**循环检测**拦住目标不可达时的无限重试
  
（同一工具 + 同一参数连续 3 次即判定无进展，注入收尾指令让模型给结论，而不是烧光 API 额度）；外部工具参数里的文件路径
  
必须位于项目目录内且存在（防止把 `-o C:\Windows\...` 当成白名单缺口）。
换壳重复也拦：同一外部工具 + 同一套选项、只换取值连打 4 次（比如反复试
`curl -w %{...}` 碰运气）同样判无进展。

**软警告管不住固执的模型，所以有第二道闸。** 实测踩过：注入"请给结论"的
收尾指令后，模型嘴上答应、下一轮照样把**一模一样的请求**再发一次——
屏幕上一串相同的包，只有延迟在变（换手机热点时会误以为是不同请求）。
所以判定死循环的**那个指纹会被记进拒绝集**，之后再原样重调时**请求根本不发出**，
直接在工具结果里回一段 `[执行被拒绝]`：说清为什么拒（同样的请求同样的失败，
重试第 N 次不会有新信息）、什么仍然允许（换参数 / 换路径 / 换 HTTP 方法 /
换 UA / 换工具都正常执行）、退路是什么（基于已有证据给结论，探不到就说
「当前证据不足以判定」）。拒绝集**只在本轮 `send()` 内有效**——下一轮用户
明确要求重试同一请求是合法的，不能带着上一轮的拒绝状态。

**大输出不是死路。** 外部工具结果超过 6000 字符时，完整内容自动保存到
`output/tool-output/` 下的文件，截断提示会告诉模型用 `read_file` 的 **grep 定位
模式**去找关键行——模型不需要、也不应该靠反复试输出选项去看被截断的部分。

**单轮不再有硬性步数上限。** 早先用 `max_steps=12` 硬截断，模型连续调工具推进任务时会被中途切断，用户看到的是半截结论，还得再敲一句「继续」。现在循环由「模型不再要求调工具」自然终止，只有检测到无进展重复才收尾。

**工具执行异常一律转成文本回灌，不向上抛。**&#x6A21;型需要看到"我失败了、原因是X"，
  
才能换方案；直接抛异常终止整轮，等于让它在信息缺失的情况下瞎猜。

### 4.1.1 手工验证的漏洞必须登记（`record_finding`）

自动探针只跑**通用 payload**。遇到需要特定构造的验证，它必然打不中：

| 漏洞类型 | 为什么探针打不中 |
|----------|------------------|
| SQL 注入 | 需要特定闭合语法（如以 `'))` 结尾） |
| 文件读取 | 需要 null byte 或特定编码绕过 |
| 越权/IDOR | 需要先拿到另一个角色的 token 再做对比 |

模型会用 `curl` / `http_request` 手工验证出这些漏洞，但**结果只存在于对话里**——
`findings` 列表看不到，导出报告里也没有，等于这次验证白做。

实测：一次 Juice Shop 测试，模型手工验证出 **14 个漏洞（含 8 个 Critical）**，
而 `findings` 里只有探针自动登记的 **2 条**（CORS、CSP）。报告里就只显示 2 项。

所以有了 `record_finding`：

```
record_finding(name, severity, matched_at, evidence, remediation, category)
```

**`evidence` 是必填的**，且为空时直接拒绝登记——项目「证据优先」的地基：
没有原始报文/回显支撑的判断只是猜测，不该进交付物。

登记后发现会带上 `manual_` 前缀与 `detector=manual`，与探针发现区分开。
写报告的正确顺序是：`findings` 看现状 → 补登记遗漏的 → `export_report`。

**登记时怎么填才不算白测**（三条纪律，也写进了系统提示词）：

| 参数 | 怎么填 |
|------|--------|
| `payload` | 你**真正发出去**的那一段（Burp 里复制整段，含请求行与头）。只写 `GET /x` 读者看不出 payload 长什么样，无法复现 |
| `response` | 服务端**真正返回**的整段（含状态行）。**不要**把「我判断这是漏洞，因为…」写进来——那是 `evidence` 该干的事。传了它就自动结构化并落盘 Burp 式报文；不传则尝试用最近一次同 URL 的响应兜底 |
| `evidence` | 研判依据：为什么这段回显能证明漏洞成立（泄露了哪个字段、越权读到了谁的数据） |

一句话：**`evidence` 说"为什么"，`payload`/`response` 给"是什么"**。三者混在一起，
报告里就会出现"`<<< 响应:` 下面是一段中文说明"这种最糟糕的形态。

**目标归属校验（防串线）**：登记时若 `matched_at` 的主机与当前会话目标
**形态不一致**（目标是域名却登记 IP，或目标是 IP 却登记域名），登记会被直接
拦下并提示先 `/target` 切换目标。原因很实在：模型经常顺手测了别的地址
（SSRF 反射出的内网 IP、扫到的邻居站），回来却用主域名登记——于是报告里出现
一条"某域名上的漏洞"，而证据其实来自另一个系统。同形态不同主机（子域名、
多主机业务）一律放行，那是正常业务形态。

### 4.1.2 `max_tokens`：静默截断是长文本的头号敌人

OpenAI 兼容接口达到 `max_tokens` 时**不报错**，只把 `finish_reason` 置为
`length` 并返回半截内容。表现极具迷惑性——模型会开始重复
「## 四、未测项」这类标题，看起来像模型发疯，实际是被砍断了。

两处防御：

| 位置 | 措施 |
|------|------|
| `stream_chat` | 默认 `max(cfg.max_tokens, 8192)`——`cfg.max_tokens`（2048）是给短问答准备的 |
| `stream_chat` | 检查每块的 `finish_reason == "length"`，截断则 yield error 并**不再发 `done`**，避免上层把半截当成完整 |

流式报错文案会直接告诉模型「分批处理（例如一次只分析 3-5 个目标）」，
而不是让它继续在半截内容上往下编。

### 4.1.3 误报怎么删（`dismiss_finding` / `findings`）

报告里混进误报是常态，而自动探针**判断不了**其中最主要的一类——**公开演示站点**。
`demo.ikuai8.com` 这类站点本来就建给人看，「泄露」出来的配置、默认账号、
接口文档属于**设计如此**，不是漏洞。探针看到"敏感信息"照报不误。

两条入口，同一套实现（`ToolRunner.dismiss`）：

| 入口 | 用法 |
|------|------|
| CLI（历史会话） | `flower_pow findings 3 -r "公开演示站点"`　`--excluded` 看清单　`--json` 脚本消费 |
| 模型 | `dismiss_finding(ref="3", reason="…")`　`dismiss_finding(ref="3", undo=true)` |

> 以前会话内还有一条 `/fp` 命令，现在**已下线**：误报排除的语义（编号怎么算、
> 撤销怎么做、要不要落排除清单）只留一份实现，多一个入口就多一处会走偏的地方。
> 会话里要排除误报，直接跟模型说"第 3 条是公开演示站，排除它"即可。

**默认是"标记"而不是"删除"**，这是刻意的：

| | 报告里 | 复核痕迹 | 撤销 |
|---|---|---|---|
| 默认（标记） | 不进风险统计与发现详情，出现在文末**「已排除的发现（误报复核）」**附录 | 保留（谁/何时/为什么） | `dismiss_finding(ref=…, undo=true)` |
| `purge`（彻底删） | 完全不出现 | 不保留 | 不可 |

> 硬删会连带丢掉"上次报的 XX 怎么没了"的解释。客户一定会问这句话，
> 报告要么能答，要么就不可信。所以想彻底删必须显式说。

**排除项按目标持久化**（`data/exclusions.json`，随 `POCS_DATA_DIR`）：
同一目标重扫时，命中的发现在**入库那一刻**就被自动标为已排除，不会又冒出来。
可以只排除一条（`poc_id` + 位置），也可以整体排除一个 POC（该探针在该站永远误报）。

两个实现上的要点：

- **编号与呈现无关**：`/findings` 的编号始终按"含已排除的全表"算。
  若按当前可见列表编号，排除一条之后后面所有编号都会平移，
  之前记下的编号就指向别的漏洞了。
- **收口在 `ScanResult.add_findings`**：以前各条路径直接
  `result.findings.extend(...)`（planner 6 处、scheduler 3 处、repl 1 处），
  任何"入库策略"都只能逐个调用点打补丁、漏一处漏一处——误报排除就是第一个
  被这个坑到的策略（历史误报不会在重扫时被自动挂上标记）。

### 4.1.4 自动判误报：回源站核验「这条是不是公开的」

上一节靠人判断。但人判断"这是公开演示站"其实也是**看证据**——只不过没被写成规则。
所以多了一条自动路径：**命中漏洞后回源站根目录取证**，够强就自动判为误报。

```bash
python flower_pow.py findings --auto      # 对已保存会话跑一轮
```

会话内则由模型调用 `check_public_finding(ref="all")` 跑一轮。
模型侧是内置工具 `check_public_finding`（`ref="all"` 批量）；`scan` 流水线在研判
之后自动跑一轮（`scan.auto_dismiss_public`，默认开）。

**取证三件套**（每个 host 只回源一次，3 个请求，结果按 host 缓存复用）：

| 取什么 | 说明 |
|---|---|
| 根页面 | 标题/正文是否自述「演示站点 / 在线演示 / 示例站点 / sandbox」 |
| 根页面的同域链接 + `sitemap.xml` | **站点自己公开挂出了这个资源**——最硬的证据，与探针怎么想无关 |
| 路径语义 + `robots.txt` | 落在 `/download/`、`/docs/`、`/firmware/` 这类公开目录算弱正向；robots **明确禁止抓取**算反向证据（扣分） |

**分档，而不是二值**——只有强档才自动删：

| 档位 | 分数 | 处置 |
|---|---|---|
| 强 | ≥ 3 | **自动判误报**。只有两条路能到 3 分：站点自己公开挂了它的链接（资源级证据），或「自述演示站 + demo 主机名 / 公开目录」叠加 |
| 中 | = 2 | **不自动删**，报"疑似公开，建议人工确认" |
| 弱 | = 1 | 只提示 |
| 无 | ≤ 0 | 正常漏洞，不动 |

> **门槛为什么不定在 2 分**：2 分 = 只有「根页面自述演示站」这一条。而这类措辞在
> **真实的产品营销页**上随处可见——"请申请演示环境"就命中 `演示环境`。
> 拿一条可能来自营销页的措辞去自动删掉整站所有发现，是在用误删风险换省事。
> 删掉一条真实漏洞的代价，远大于多留一条误报。

两条工程约束：

- **网络失败绝不当成"公开"**。抓不到根页面就如实报"无证据不判定"——
  空 title/body 一路打分也算出 0 分，但那会把"没查到"说成"查到没有"，
  两种结论对用户的意义完全不同，所以单独走一条分支。
- **证据按 host 缓存**。几十条发现共用一份上下文，不会"每条都回源"把目标打一遍。

被自动排除的项同样进报告的**「误报复核」附录**（写明取证结果），可用
`dismiss_finding(ref=…, undo=true)` 撤销。想完全关掉自动判定：`POCS_AUTO_DISMISS_PUBLIC=false`。

### 4.1.5 文件增删改：报告是「就地维护」的，不是每次生成一份

报告导出过去每次都在生成**新文件**——`report_20261012_x.com.md` → `_2.md` → `_3.md`。
改一轮、导一次，很快堆出一串近似重复的报告，用户还得猜哪份是最新的；智能体也没法
"接着上一份改"，只能整篇重写。所以补两件事：

**① 导出默认就地覆盖同一份文件**（`export_report(fmt, overwrite=True)`）。
三种格式收进**以报告主干命名的同一个文件夹**（`output/report_<日期>_<主域名>/`），
反复导出不再堆副本。要留档时传 `overwrite=false`（另存为 `_2` 文件夹）。
覆盖是可见的——返回里逐条标 `[新建]` / `[覆盖]`。

`fmt` 只认 `md / html / json / all`：**传错格式名会当场报错并列出合法值，绝不
静默"成功"却一个文件都不写**（这是真出过的事故：`fmt="markdown"` 返回"报告已
导出："但磁盘上什么都没有）。另外所有工具的实参都会先按 schema 归一类型——
模型把布尔写成字符串 `"false"` 是常态，而它在 Python 里恒为真（`overwrite="false"`
真的会去覆盖、`undo="false"` 真的会撤销误报标记）。归一在 `execute()` 一处收口，
逐个 handler 打补丁治不了根。

**② 五个文件工具**，让智能体接着改而不是整篇重写：

| 工具 | 用途 |
|------|------|
| `list_files` | 看产物目录里有什么、哪份最新 |
| `read_file` | 读原文。**两种模式**：`grep="关键字"` 定位模式（一次返回所有命中行 ±上下文，分析 JS/HTML/JSON 大文件用这个，**别逐页翻**）；`start_line`/`max_lines` 翻页模式（最后手段） |
| `write_file` | 新建 / 覆盖（写自定义说明、附录、清单） |
| **`edit_file`** | **就地替换某一段**——只动你指的那段，其余一字未动 |
| `delete_file` | 删单个文件 |

`edit_file` 要求 `old_text` **逐字符一致**，且出现次数与 `count` 相符（默认恰好
1 次）。含糊的替换比不改更糟——它可能悄悄改掉别处的同一段文字，而报告里这种
"看起来改过了"最危险。所以出现 0 次或 2 次都**拒绝执行并说明**，让模型去读原文。

> **一个必须知道的交互**：`export_report` 是**整篇重新生成**，用 `edit_file` 打的
> 补丁会被覆盖掉。工具在覆盖时会明确警告这一点。想长期保留手写内容，把它写成
> 单独的说明文件（`write_file appendix.md`）或登记进发现，别只补在报告里。

#### 安全边界：手关在产物目录里

模型可以要求写任意路径，所以约束必须落在代码里（`core/fsops.py`），不能指望
提示词。所有操作共用同一个路径校验，四道**结构性**闸门：

| 闸门 | 说明 |
|------|------|
| 只能在 `output_dir` 内 | 绝对路径、盘符、UNC、`..` 一律拒绝；最后再用 `resolve()` 的结果做一次"必须在根之内"校验 |
| **重解析点直接拒绝** | 符号链接**和目录联接**都会把读写引到根外。注意 `Path.is_symlink()` 在 Windows 上**看不见目录联接**（实测 `symlink_to` 创建出来的东西 `is_symlink()` 就是 `False`），所以改用 `lstat` + 重解析点属性判断 |
| 扩展名走**白名单** | 只允许报告类产物（md/txt/json/html/csv/xml/svg/log…）。为什么不是黑名单：黑名单永远漏（`.phtml`/`.ps1xml`/…），而这个沙箱的用途是"写报告产物"，白名单能一句话说清边界。产物目录不能变成代码投放点 |
| 不写目录、不删目录 | 删目录一条命令就能毁掉整个产物区，而工具没有任何场景需要它 |

另外：**原子写**（临时文件 + `os.replace`，中途崩溃不留半个报告）、单次写入 2 MB
上限、`edit_file` 改完超限就放弃（原文件不动）。

**读取也关在同一个沙箱里**——读不关就等于钥匙漏了：`read_file("../../.env")`
拿到 API Key，再接一发 `http_request` 就出去了。所以读写删共用一套路径校验。

**和 `readonly` 无关**：`scan.readonly` 管的是**对目标**的写操作（上传、篡改），
本模块管的是**本地产物**；导报告本来就要写本地文件，只读模式下照跑。想整体关掉
用 `scan.fs_ops_enabled` / `POCS_FS_OPS`（默认开）。

### 4.1.6 自动轮询：`/poll` —— 不用一直敲回车，穷尽了才停

会话里每轮之间要**手工回车**才继续。跑一个站点往往十几轮，人得一直守着敲；
而"什么时候算测完"也只能靠人自己看。`/poll` 把这两件事一起解决：

```
/poll          用配置上限（scan.auto_max_rounds，默认 12；0 = 不限）
/poll 20       这次最多 20 轮
--poll         CLI 非交互等价物（配 --classic 或默认 Agent）
```

**穷尽判据：连续 2 轮完全没有新增**。"有新增"指三者之一：

| 信号 | 为什么算 |
|------|------|
| 新增资产 | 挖到新的接口/路径/端口 |
| 新增发现 | 验证出漏洞 |
| 新增业务模型条目 | 建模阶段的主要产出**既不是资产也不是发现**，不数它会把成功的建模轮误判成空转 |

**为什么要求连续两轮**：单轮没产出可能是"这轮在研判/整理"，不代表没得测了。

> **判据只看硬状态，不看"下一步建议"。** 这一点是**实测纠正**的：最初把"没有
> 下一步建议"也算作空转条件，测试直接失败——`Planner._suggest()` 是**阶段驱动**的
> 兜底文本（迭代阶段恒为"继续迭代或导出报告"），**每轮都非空**，那个条件永远
> 不成立，"穷尽了才停"就退化成"每次都跑到上限"。建议文本是给人看的旁白，
> 不是可依赖的负信号。

**硬上限是安全阀，不是穷尽判据**：Agent 可以每轮都调一次工具、每轮都不产出结论，
那样永远判不出穷尽、token 会一直烧。所以另设 `scan.auto_max_rounds` 兜底。
到上限的措辞与"已穷尽"**严格分开**：

```
✅ 已穷尽：连续 2 轮无新增资产/发现/建模项。自动轮询结束……
⏸ 已到自动轮询上限 12 轮，**不是测完了**。要继续就再来一次（或把上限调大：……）
```

混着说的后果很实际：用户会以为覆盖面完整了。

REPL 与 CLI 共用同一套实现——判定在 `core/progress.Exhaustion`，循环在
`core.progress.poll_until_done`，两处只提供"怎么跑一轮"。行为不会出现两套。
Ctrl-C 随时中断（驱动层**刻意不吞** `KeyboardInterrupt`，否则 Ctrl-C 要等到下一轮
才响应），会话逐轮存盘，中断不丢东西。

### 4.2 两层能力：机器上装了什么，模型就能多用什么

Agent 的能力天花板是本机现状。用 `python flower_pow.py tools` 可随时查看：

| 层          | 数量              | 说明                                                   |
| ---------- | --------------- | ---------------------------------------------------- |
| **内置工具**   | 22 个            | 纯 Python 包装本项目已有模块，**零外部依赖**，没装任何东西也能用               |
| **外部 CLI** | 12 个内置 + 你自己登记的 | 探测到才暴露给模型（当前机器可用 4：nmap / dirsearch / curl / sqlmap） |

> 没装的东西**不会**出现在给模型的工具清单里——否则它会兴高采烈地调用，
>   
> 然后拿到一句"命令不存在"，浪费一整轮预算还得出错误结论。

### 4.3 装了新工具却不被认？`discover` + 自定义清单

外部工具清单**分两半**：12 个内置项在 `core/tools/external.py`，你自己装的写进
  
`data/tools.local.yaml`（首次运行自动生成带注释的模板）。两者合并后探测，
  
**同名以自定义为准**——想换掉内置项的参数白名单也可以。

> **"工具存在"和"工具被登记"是两件事，程序只认后者。**
>   
> PATH 里明明有、环境变量也配对了，但不在任何清单里，就永远不会被探测。
>   
> 这不是 bug，是不猜名字的后果——见下。

```bash
python flower_pow.py tools                # 看已登记工具的探测结果
python flower_pow.py discover             # 看 PATH 里存在但清单没登记的
python flower_pow.py discover --grep sql  # 按关键字筛（推荐，PATH 里通常有几百个 exe）
python flower_pow.py discover --all       # 列全部（先过滤再看）
```

登记格式（`data/tools.local.yaml`）：

```yaml
tools:
  - key: nuclei-pd
    bins: [nuclei, nuclei.exe]     # 命令行文件名，不是目录
    category: 模板扫描
    desc: 社区模板引擎，跑只读模板。
    flags: [-u, -tags, -severity, -silent, -no-color, -duc]   # 白名单
    version_args: [-version]
```

改完**直接跑下一条命令就生效**，不用重启、不用改 Python 源码。

#### 为什么不自动扫描 PATH 并猜测哪些是安全工具

实测过，走不通。本机 PATH 有 **2660** 个可执行文件，按 `scan`/`sql`/`crack`
  
之类的词筛，出来的绝大多数是同名噪音：

| 筛出来的名字                                | 实际是什么        |
| ------------------------------------- | ------------ |
| `secpol` `doskey` `charmap` `fixmapi` | Windows 系统组件 |
| `psql` `sqlite3` `sqldiff` `initdb`   | 数据库客户端       |
| `ffprobe`                             | 视频工具         |
| `nettle-hash` `ssh-keyscan`           | 开发库附带        |

把 `psql` 当"SQL 注入工具"交给模型，比不给它更糟。所以 `discover` 的定位是
  
**把候选摆给人看，由你确认**——判断"这是不是安全工具"这件事不能靠猜。

`discover` 已经过三轮噪音收敛（跳系统/开发目录、滤GNU coreutils 与
  
conda 家族），本机从 525 条收敛到 265 条，剩下的都是正常工具名。

#### 两个必须知道的限制

1. **只支持命令行工具。** IDA、Burp、蚁剑、Cobalt Strike 这类 **GUI 程序
     
   无法通过 PATH 探测**——它们没有 CLI 入口，登记了也不会被调用。
2. **同名不同物非常常见。** `httpx` 就有两个毫无关系的实现：ProjectDiscovery
     
   的渗透工具，和 Python `httpx` 库附带的命令行包装器（本机 PATH 里就是后者，
     
   版本 0.28.1，只是个 HTTP 客户端）。登记前先敲 `工具名 -version` 核对。

内置工具按职责分七组：

| 分组   | 工具                                                                                        |
| ---- | ----------------------------------------------------------------------------------------- |
| 编排   | `set_target`（设定会话目标）、`session_state`                                                      |
| 侦察   | `http_request`、`recon_fingerprint`、`recon_ports`、`recon_paths`、`recon_js`、`recon_openapi`、`recon_subdomains`、`js_audit`、**`search_assets`（网络空间测绘统一入口：Quake/FOFA/Hunter/ZoomEye 按 key 自动路由、结果合并去重，Agent 只看到这一个工具，平台扩展无感）** |
| 检索   | `rag_search`、`poc_list`、`cve_intel`                                                       |
| 业务   | `login`（自动定位登录端点与字段，能还原纯文本 SVG 验证码）                                                       |
| 验证   | `authz_probe`（未授权/IDOR/敏感字段三类批量探测）、`sqli_probe`、`exploit_probe`、`run_pipeline`（跑完整流水线）                                 |
| 报告   | `findings`（带编号，可含已排除）、`dismiss_finding`（**误报排除/撤销**）、`check_public_finding`（**回源核验公开性，自动判误报**）、`record_finding`（登记手工验证的漏洞）、`export_report`（**默认就地覆盖同一份报告**） |
| 文件   | `list_files`、`read_file`、**`edit_file`（就地改某一段）**、`write_file`、`delete_file`（全部关在 `output/` 内，见 §4.1.5） |
| 外部工具 | `external_tool`（统一入口，参数受白名单约束）                                                            |

自定义工具**同样受三道闸门约束**：只暴露探测到的、参数过白名单、
  
`intrusive: true` 在只读模式下被拒绝、`bins` 支持绝对路径（可登记不在 PATH 里的工具）。

外部工具**不为每个生成单独 schema**，而是统一收敛成 `external_tool` 一个入口：
  
参数是完整 argv 数组，逐项过白名单校验。这样模型学到的调用格式永远只有一种，
  
新增工具也不需要改提示词——只改探测清单即可。

### 4.4 子域批量扫描（`subs`）

`scan` 只接单个 URL。子域是另一类问题：**一个主域下几十个子域，
  
真正在线的可能只有三五个**，但每个都要跑端口扫描 + 字典爆破 + 33 条 POC。
  
100 个子域全跑 POC 与"筛出值得深挖的子域"是两件事，混在一起只会
  
得到几百条低危配置缺失，把真正的问题淹掉。

```bash
# 输入可以是：文件 / 纯文本 / 剪贴板（-）
python flower_pow.py subs -            # 扩展复制的那份 JSON
python flower_pow.py subs result.json
python flower_pow.py subs "http://a.example.com
http://b.example.com"          # findSubDomain 的复制内容直接粘

python flower_pow.py subs - --root example.com      # 只扫它的子域
python flower_pow.py subs - --mode full             # 每个在线子域跑完整流水线
python flower_pow.py subs - --dirsearch true        # 对在线子域并行跑路径爆破
```

**输入格式兼容 findSubDomain 的四段结构**（截图里那个）：

| 字段                         | 处理                                      |
| -------------------------- | --------------------------------------- |
| `域名` / `hosts` / `domains` | 扫描目标                                    |
| `URL`                      | 取主机名作为目标                                |
| `邮箱`                       | **抽取域名**——邮箱的域名常是未链接的子域，不该丢             |
| `IncompletePath`           | **主动忽略**。它是路径片段（`/static/`、`/l/`），不是主机名 |

主域收敛是强制的：`--root example.com` 会把 `cdn.jsdelivr.net` 这类
  
外链全部排除。**不收敛的话，"扫我的子域"会变成"扫整个互联网的抽样域名"。**

`--dirsearch true` 用的是 dirsearch 自己的 `-l` 批处理模式，
  
而不是每个子域起一个进程——它内部已有多线程，这样更快也更省进程。


输入来源不限：文件路径、字面量文本、`-`（读剪贴板）。
浏览器里复制的域名列表、`findSubDomain` 之类的工具输出、
任何抓包结果里挑出的主机名，粘进文件或剪贴板都能直接喂给它。

### 4.5 子域从哪来：被动枚举 + 排列组合

`subs` 命令解决"**给我一批子域，我并发扫完**"。但第一步其实是反过来——
**这批子域从哪来**。这两件事输入输出都不一样，所以分开：

| 模块 | 职责 | 输入 → 输出 |
| --- | --- | --- |
| `collectors/subdomain_extract.py` | **找**子域 | 一个主域 → 一列候选主机名 |
| `core/subdomain.py` | **扫**子域 | 一列主机名 → 一份报告 |

当前只做两件**不需要任何外部工具**的事：

```
1. 多源被动枚举            并发查 5 个公网被动源（见下表），
                          找出该主域下真实出现过的子域
                          → 不发一个请求给目标，零攻击面、零被拉黑风险
2. 前缀排列组合            dev.api.x.com → api.x.com（减前缀）
                          staging.x.com → test.x.com（换同级前缀）
                          → 产出标注为"猜测"，需探活验证
```

### 为什么是"多源"而不是"只查 crt.sh"

最初只有 crt.sh 一个源。实网踩到 **crt.sh 整站 502**（连根路径 `https://crt.sh/`
都返回 nginx 502），子域枚举**完全失效**，最后只能拿用户手工提供的清单继续：

> `gdust.edu.cn` 一役，crt.sh 持续 502，被动枚举与排列组合都返回 0，
> 报告里只能写"子域攻击面本轮未能覆盖"。事后用 hackertarget 一查，
> 同域拿到 **21 个子域**，其中 9 个是用户清单里没有的
> （`webvpn` / `jump` / `m` / `zikao` / `pxg` / `gkjx` / `gksys` / `bkzj` / `zbtd`）——
> 也就是**整整一批被漏掉的攻击面**。

**单点数据源在实网里不可接受**：任何公网被动源都会挂、会限流、会被墙。

| 源 | 入口 | 特点 / 坑 |
| --- | --- | --- |
| **crt.sh** | `https://crt.sh/?q=%.X&output=json` | 证书透明日志，可信度最高；**会整站 502** |
| **hackertarget** | `https://api.hackertarget.com/hostsearch/?q=X` | 命中率高；免费 **50 次/天**，超限返回正文 `API count exceeded` 而**不是** HTTP 错误——只看状态码会静默失真 |
| **RapidDNS** | `https://rapiddns.io/subdomain/X?full=1` | 返回 **HTML**，域名在 `<tbody>` 每行第一个 `<td>`；"找到 0 条"不是错误，但**结构变了**必须当失败上报 |
| **urlscan.io** | `https://urlscan.io/api/v1/search/?q=domain:X` | `domain:` 过滤**很松**，实测会混进完全无关的域名（查 `example.com` 混进 `huffpost.com`）——所以结果必须逐条按后缀严格收敛 |
| **OTX** | `otx.alienvault.com/.../passive_dns` | 限流很严（实测直接 429）；**404 是"没记录"不是失败** |

聚合语义（都在测试里锁住）：

- **并发**——总耗时 ≈ 最慢的那个源，不随源数累加。crt.sh 挂的时候是"一直转"，
  串行跑会把时间全耗在它身上；另有 `SOURCE_TIMEOUT` 源级硬超时兜底。
- **每源独立降级**——任一源抛异常只让那一项变空集 + 留一条 note，其余源照常出结果。
- **失败必须可见**——"源挂了"和"源说没有"是两回事。前者一定留痕，
  绝不静默成"该域没资产"（这正是上面那次事故的教训）。
- **归属按可信度**——同一主机名出现在多个源时，按 `SOURCE_PRIORITY`
  归给最可信的那个，展示时标出真实来源名。

**crt.sh 的四个坑**（都已在代码与测试里处理）：

| 坑 | 处理 |
| --- | --- |
| 记录是 `name_value` 换行分隔 | `a.x.com\nb.x.com` 必须拆开，否则整串当一个主机名 |
| 通配符 `*.x.com` | 剥星号；剥完等于主域的直接丢弃 |
| 主域自身混在里面 | 它已经是被测目标，不算"子域" |
| **入口会 502** | 整站故障时**自动换源**（见上表），不再颗粒无收 |

### 主域抽取：多段公共后缀必须最长匹配

`main_domain()` 曾经天真地"取最后两段"，于是：

```
gdust.edu.cn    →  edu.cn     ← 错！查询 %.edu.cn 会拉回全国高校的域名
example.com.cn  →  com.cn     ← 错！
x.example.co.uk →  co.uk      ← 错！
```

后果是**双重**的：一是查询 `%.edu.cn` 拉回几十万条记录、必然超时/502 且污染结果；
二是排列组合会基于 `edu.cn` 产出 `dev.edu.cn` 这类垃圾。

现在内置一份**精简公共后缀表**（`PUBLIC_SUFFIXES`，覆盖 `.edu.cn` / `.com.cn` /
`.co.uk` / `.co.jp` / `.com.hk` 等现实里真会踩的多段后缀）做最长匹配，
**刻意不引 `publicsuffixlist`**（为一个字符串判断拉一个包 + 一份需定期更新的数据文件不划算）。
输入本身就是公共后缀（如直接给 `edu.cn`）时返回空，明确说"解析不出主域"，
比硬造一个更有用。

> **排列组合为什么只做"减前缀 / 换前缀"，不做"给主域加前缀"？**
> 后者是 wordlist 爆破的活。塞进"被动枚举"里会让用户以为只是查了个日志，
> 实际发了一堆猜测请求——这不符合"被动"的语义。
>
> 换前缀还加了个**互斥条件**：仅当其余部分**恰好就是主域**时才换。
> 不加的话 `admin.portal.example.com` 会被当成 `admin` + `portal.example.com`，
> 产出 `dev.portal.example.com` / `portal.portal.example.com` 这类两层堆叠垃圾——
> 实测 6 个真子域被放大成 **24 个噪音候选**，加上条件后收敛到 11 个。

**两个自动接入点**（不用手动敲工具名）：

- `core/planner.py` 的 `_recon()`：第 1 轮信息收集时，目标是域名就自动跑一遍被动枚举，产出写进 `session.result.assets`
- `core/scheduler/recon.py` 的 `_phase2_recon()`：`scan` 单目标流水线同样在侦察阶段扩展子域面

子域资产还会**按前缀拆词**喂给 RAG（`admin.portal.x.com` → `admin`、`portal`），
因为"环境与角色"正是 POC 匹配关心的维度；整串塞进去只会稀释语义。

Agent 也可以主动调：`recon_subdomains(domain, passive_only=True)`。

### 4.5.1 接口从哪来：JS 里挖，四个限制都必须放开

后台的接口路径**只存在于前端 bundle 里**——没有 OpenAPI 文档，也没有导航链接。
不读 JS 就永远发现不了。但读 JS 这件事本身有四个很容易踩死的坑，
任何一个都能把结果压到个位数：

| 限制 | 旧值 | 后果 | 现在 |
| --- | --- | --- | --- |
| 单文件抓取上限 | `max_body_capture` 4KB | 只扫到 bundle 开头的 license 注释 | `js_max_bytes` 2MB |
| 接口路径前缀白名单 | `api\|v\d\|rest\|service\|graphql\|admin\|user\|auth\|login\|upload\|download` | `/role/getAll`、`/oa/noticeType/getAll`、`/e/aspx/get_info.aspx` 一条都匹配不上 | 去掉白名单，改**结构判别** |
| 只读 HTML 的 `<script src>` | 不跟进 `import` | 路由懒加载的 `*-api-*.js` chunk 永不下载 | 模块图 BFS，深度 `js_max_depth=2` |
| 文件数预算 | 12 | 现代工程一个页面就 20+ chunk | 120（接口 chunk 优先下载） |

**结构判别**的眼：多段、至少一段含字母、不是静态资源、不是 MIME、
不是 hash 路由（全 16 进制段）、不是 import 的相对引用。放宽的是"猜业务词"，
收紧的是"一眼假"——`/dorm/fun/bed/whole` 能进，`/static/img/logo.png` 进不来。

压缩后的写法也得吃：`o("monitor/online/query",t)` 是 1 字符别名 + 无前导斜杠，
绝对路径正则抓不到。所以另有一条"函数调用实参"规则，配合 JS 里的
`baseURL:"/api"` 拼回 `/api/monitor/online/query`——不拼前缀，拿去探活只会 404。

**放宽一定带来噪声**，但不能靠丢：`/gi`、`/bwc`、`/tzgg` 这类导航目录名
和真接口长得一样，丢了可能丢掉 `/dorm`。所以只排序不丢弃——
`ep_rank()` 依次看「后台类 → 带 `.aspx/.php/.do` 后缀 → 段数多 → 短」，
让真接口占住 `js_logic_max_endpoints=60` 的探测名额。

实测（同一目标、同一份 JS，旧正则 vs 新提取器）：

| 目标 | JS 文件 | 旧版 | 新版 |
| --- | --- | --- | --- |
| `www.gdust.edu.cn` | 13 | **0** | **40** |
| `pxg.gdust.edu.cn` | 4 | **0** | **53** |
| `zlgc.gdust.edu.cn` | 5 | **0** | **5** |
| `zbtd.gdust.edu.cn` | 3 | 8 | 12 |
| `cas.gdust.edu.cn`（Vue SPA） | 120 | **0** | **122** |

pxg 挖到的 `/dorm/fun/bed/whole`、`/reporting/base/leaveapply`、
`/collection/StuInfoSupply/downloadDataTemplate` 这些，旧版**一个都看不到**。
cas 是纯 SPA，修复前 0 项，修复后 122 项，连 `/monitor/log/export`、
`/monitor/log/batchDelete` 这种深埋在 chunk 里的都出来了。

**SPA 还多一层坑：裸相对路径。** Vite 的 chunk 清单写成
`["js/vue-router-a1.js","js/monitor-api-390a.js",...]`——不写 `./`，
它相对的**不是**当前文件目录，而是入口文件的父目录。按"相对当前目录"解析会得到
`/cas-admin/js/js/monitor-api.js`（404）。判据是「当前目录名恰好等于路径首段」：
`/cas-admin/js/` 对上 `js/` → 回退一级。这一条不修，监控模块的 5 个接口永远挖不到。

**预算永远不够，所以要选着下。** cas 的模块图第 2 层有 179 个候选，
120 的预算覆盖不全。`_chunk_priority()` 让名字里带 `api`/`service` 的
chunk 先下（`monitor-api-390a46d5.js` 正是这一类），vendor / echarts /
图标这些排后面——同层候选也按这个顺序取，不是先到先得。

> **静态提取 ≠ 可访问。** 这里只回答"前端认为有哪些接口"。
> 是否未鉴权、是否越权，要由 `js_audit` 逐条发一次免凭证 GET 才知道
> （`js_logic_probe_api`，默认开）。

### 4.6 本机代理：有代理就走代理（内网也走，端口扫描也走）

渗透测试机上通常**同时**挂着两套代理，而它们的用途不同：

| 来源 | 典型场景 | 变量 / 位置 |
| --- | --- | --- |
| 环境变量 | 上一层工具链注入（Burp / mitmproxy / 公司网关） | `HTTP_PROXY` / `HTTPS_PROXY` / `ALL_PROXY` |
| Windows 系统代理 | Clash / v2ray 这类分流工具 | 注册表 `Internet Settings` |

**原来的行为有个致命问题**：项目一律 `trust_env=False`，把两套代理全部无视。
结果是"我明明挂了 Burp / Clash，扫描却全程直连，代理里什么也看不到"。

现在启动时会**自动探测**，探测到就默认走代理：

```bash
python flower_pow.py proxy                      # 只看检测结果
python flower_pow.py proxy -t http://a.com/     # 看这个目标会不会走代理
```

实测输出（本机开着 env 代理 `127.0.0.1:54426`）：

```
$ python flower_pow.py proxy
本机代理检测
  配置 proxy        : http://127.0.0.1:54426
  自动探测开关       : 开
  探测结果           : http://127.0.0.1:54426（来源 env:http）
  原始取值           : {'HTTP_PROXY': 'http://127.0.0.1:54426'}

$ python flower_pow.py proxy --target https://example.com/
  决策               : 走代理 http://127.0.0.1:54426

$ python flower_pow.py proxy --target http://192.168.10.128:8899/
  决策               : 走代理 http://127.0.0.1:54426
```

**默认语义：所有目标都走代理——包括内网与本机，且不越权替 Clash 做分流。**

| 目标类型 | 走不走代理 | 为什么 |
| --- | --- | --- |
| 公网域名 | ✅ 走 | 这正是 Burp/Clash 要拦的流量 |
| 内网 IP（`10.` / `172.16-31.` / `192.168.`） | ✅ 走 | **不拦截**——隐藏与路由交给 Clash 节点决定 |
| 回环 / `localhost` / `*.local` / `*.internal` | ✅ 走 | 同上 |
| 端口扫描 | ✅ 走 | 经 SOCKS5 / HTTP CONNECT 隧道转发（见下） |

> **为什么"内网也走"、并且不替 Clash 做分流决策？**
> 旧版把"内网一律直连"写死成硬规则，结果挂了 Clash mixed 端口也抓不到
> 内网流量——真实 IP 直接暴露给目标方，代理等于白挂。
> 现在本机代码只负责"把请求送进代理"，**怎么出网由 Clash 节点决定**。
>
> **Windows 的 `ProxyOverride` 分流表也被丢弃了。** 那张表塞满内网 IP
> （`10.*;172.16.*;192.168.*;<local>`），是给**浏览器/系统应用**用的规则；
> 拿它当"直连例外"会让扫描内网目标时静默直连、真实 IP 暴露——
> 恰恰是要消灭的行为。唯一的直连出口是 `scan.no_proxy`——
> **你自己写进配置的显式声明**，属于有意为之而非副作用。

**端口扫描怎么走代理？** 端口扫描是裸 TCP（`asyncio.open_connection`），
HTTP 代理只转发 HTTP 语义的请求——**但 SOCKS5 的 CONNECT 命令可以，
HTTP 代理的 `CONNECT` 方法也可以**。所以 `core/tunnel.py` 自带一个最小
SOCKS5 客户端（不依赖 `socksio`），按顺序尝试：

1. 代理是 `socks5://` → SOCKS5 握手 + CONNECT；
2. 代理是 `http://` → 先试 **HTTP CONNECT** 隧道（Burp 场景），
   失败再试 **SOCKS5**（Clash mixed 端口场景）；
3. 代理完全不支持隧道 → **自动降级直连**，不因为代理让整个扫描失败。

隧道结果直接映射成端口状态：连接成功 = `open`，代理回
"connection refused" = `closed`，不可达 / 超时 = `filtered`。

**配置**（`config.yaml` 的 `scan` 段）：

```yaml
proxy: null                # 显式指定，如 http://127.0.0.1:7897；留空则自动探测
no_proxy: []               # 唯一直连出口（你自己写）：域名后缀 / CIDR / 192.168.* 通配
proxy_autodetect: true     # 自动探测（环境变量 > Windows 系统代理）；false 时只认 proxy 字段
```

`proxy` 留空 + `proxy_autodetect: true` = 完全交给系统：
自动读取 `HTTP_PROXY` / `HTTPS_PROXY` / `ALL_PROXY` 环境变量，
读不到再读 Windows 注册表的 `ProxyEnable` / `ProxyServer`——
也就是 Clash 配好就不用管，本机自动接上。

优先级：**显式配置 > 环境变量 > 系统代理**。你在 `config.yaml` 或
`POCS_PROXY` 里写死的东西永远最高——它代表"我就是要走这个"，不做自动化覆盖。

决策全部收敛在 `core/proxy.py`，所有 HTTP 客户端（检测器 / 采集器 / 登录器）
共用同一个入口 `build_client_kwargs()`；端口扫描则共用同一个
`resolve_proxy_for()`，不会出现"HTTP 走代理但端口扫描直连"的割裂。

> **代理不支持 socks5 怎么办？** httpx 的 SOCKS 支持依赖可选依赖 `socksio`，
> 没装时构造客户端就抛 `ImportError`。`httpx_compatible_proxy()` 会在缺
> `socksio` 时把 `socks5://` 自动降级成 `http://`——Clash 的 mixed 端口
> 两种协议都接受，所以照常工作。

### 4.7 被 WAF 拦截时自动降速（`-t 1` 重试）

路径爆破一定会撞上 WAF / 限流。dirsearch v0.4.3 **没有内置退避**——
它有 `--skip-on-status` / `--retries` / `--max-rate` / `--delay`，
但都要人手动配，没有「扫到一半被限流 → 自动降速接着扫」这回事。

所以 `collectors/dirsearch_runner.py` 负责这件事，两处调用点共用
（单域 `path_scan.run_dirsearch` 与子域批量 `flower_pow._subs_dirsearch`）：

```
第一遍  -t 10  正常速度
   ↓ 检测到拦截
第二遍  -t 1 --delay 0.3 --max-rate 5 --retries 2   ← 单线程 + 限速
   ↓ 仍被拦
如实报告「目标存在 WAF 行为检测」，不再重试
```

**为什么单线程还要配 `--delay` / `--max-rate`**：单线程只解决并发压力，
不解决请求速率。WAF 限流看的是「单位时间请求数」，三管齐下才真的慢下来。

**拦截怎么判定**（`looks_blocked`）：不能只看单个 403/429——目标本来就有
大量 403（后台未登录）。用四条**组合信号**，命中 2 条及以上才判拦截：

| 判据 | 含义 |
| --- | --- |
| 429/503 占比 >=10% | 限流特征 |
| 403 占比 >=80% 且无其他状态码 | WAF 特征 |
| 命中 `cdn-cgi` / `captcha` / `__cf_` 等 WAF 路径 | 防护层响应 |
| 有结果但无一个有效状态码 | 请求被吃掉 |

单条会把「站点真的全 403」误判成拦截，白白降速重跑一遍，所以阈值保守。
实测「真·全站后台 403」**不会**触发降速。

单线程重试后仍被拦，说明不是速率问题而是行为检测，**此时继续重试只会
浪费时间和暴露意图**，所以如实报告并停止。

排查用：

```bash
# 看 dirsearch 真实路径
python -c "import shutil; print(shutil.which('dirsearch'))"
# 子域批量的过程记录（会落盘）
cat output/dirsearch_subs_<时间戳>.json
```

落盘的 JSON 含 `threads_attempts`（每轮线程数）、`throttled`（是否降速过）、
`block_reasons`（每次判定的理由）、`events`（完整事件流），便于事后复盘。

### 4.8 dirsearch 参数的三个坑（v0.4.3 实测）

调 dirsearch 时踩到的、**报错信息完全指不到真正原因**的三个问题，
已固化在 `dirsearch_runner.build_argv` 里：

| 坑 | 现象 | 正解 |
| --- | --- | --- |
| `-s 200,301,...` | `FileNotFoundError: '200,301,302,401,403'` | `-s` 在该版本是 `--session`（会话文件），状态码要用 `--include-status=` |
| `--plain` | `error: no such option: --plain` | 它是 `--format` 的可选值之一，要 JSON 得写 `--format json` |
| 读 `statusCode` / `contentLength` | 解析出 `status=0`、`size=None`，所有结果被当无效 | 真实字段是 `status` / `content-length`（**带连字符**） |

前两个会让 dirsearch 直接报错退出，第三个更隐蔽——不报错，但每条结果的
状态码都是 0，于是**全部结果被过滤掉，看起来像「dirsearch 没跑出东西」**。
在修正前，这个集成实际上从未真正产出过结果。


## 5. RAG 是怎么做的（以及为什么不是最优雅的方案）

### 5.1 为什么自己实现向量库

POC 库只有几十到几百条量级，引入 Chroma 意味着多一整棵依赖树
  
（chromadb → onnxruntime → …）而收益几乎为零。所以用**纯Python** 实现：

```
文本 → 分词 → hash 到固定维度 → TF-IDF 加权 → L2 归一化 → 落盘 JSON
```

好处：索引是**可读的 JSON**（出问题能直接打开看），零重依赖，
  
在只有 httpx + yaml 的机器上也能跑完整流程。检索接口只有 `search()` 一个方法，
  
将来 POC 涨到数千条以上，换成 FAISS / Qdrant 只需替换这一个实现。

### 5.2 混合检索：BM25 为什么是必需的

最初只用 TF-IDF 余弦，结果几乎不可用。实测：

```
query = "Apache Tomcat/9.0.65 java tomcat"
Struts2 POC 的余弦相似度 = 0.033        ← min_score 阈值直接把它过滤掉了
```

根因是**小语料下的稀疏余弦失真**：query 向量的非零维度远多于文档向量
  
（指纹里都是服务器名、标题、各种标识符），余弦被系统性压低。

BM25 对"精确命中某个词"给予高权重，且分数不随词数稀释。最终采用：

```
hybrid = 0.35 × 归一化余弦 + 0.65 × 归一化 BM25
```

余弦管模糊/语义，BM25 管精确术语。权重偏向 BM25——安全测试里技术栈名字的
  
精确匹配价值远高于语义相似。改造后的实测（4 个场景 top-1 全部正确）：

| query                               | top-1                 | 得分    |
| ----------------------------------- | --------------------- | ----- |
| `Apache Tomcat Struts2 java action` | `cve-ssti-detection`  | 1.000 |
| `nginx php cookie 安全头 CORS`         | `hdr-cors-wildcard`   | 1.000 |
| `spring boot actuator 调试端点`         | `path-debug-endpoint` | 1.000 |
| `php cgi 参数注入 任意代码执行`               | `cve-php-cgi-args`    | 1.000 |

### 5.3 RAG 的先天盲区与基线集

**检索的本质是"找相似"，而有些漏洞与技术栈毫无关系。** 实测：

```
Spring Boot 目标上 path-git-config 的融合得分 = 0.000
                        path-source-code     = 0.000
```

`.git/config` 泄露、source map 暴露这类漏洞，在向量空间里与任何 Web 指纹都不相似，
  
**任何检索都召不回它们**——而它们恰恰是最该查的。

解决办法不是调大 `top_k`（那会牺牲精准度），而是把"必查项"显式声明出来：

```yaml
always_run: true      # 通用基线：与技术栈无关，任何 Web 目标都必查
```

外加两条自动规则：`header_check` 类无条件并入（判断"某个响应头在不在"
  
与目标是什么技术栈毫无关系，它问的是"这个头在不在"）。

这个兜底放在**两个地方**——`kb/retriever.py`（RAG 正常路径）和
  
`core/scheduler/match.py::_merge_baseline`（降级路径），
  
因为 RAG 被禁用或索引损坏时会走降级分支，那里也要覆盖到。

### 5.4 知识库沉淀：把扫描发现回灌成知识

前面 5.1-5.3 讲的索引都是**单向**的：人写 `poc/*.yaml` → 建索引 → 检索。
扫描结果只流向 `output/` 和 `data/sessions/`，终点是文件，不是知识。
这意味着**同一个站反复测，每次都要从头踩一遍坑**。

`kb/knowledge.py` 补上回写，形成闭环：

```
扫描 → 研判降误报 → 确认过的发现 → 知识库 → 下次同站测试时被召回
```

```bash
python flower_pow.py knowledge          # 看沉淀了多少
python flower_pow.py knowledge search "actuator 未授权"
python flower_pow.py knowledge clear    # 清空
```

两个索引文件**故意分开**：

| 文件 | 内容 | 来源 |
|------|------|------|
| `poc_index.json` | 33 条检测规则 | 人写的 YAML |
| `knowledge_index.json` | 历次扫描**确认过**的真实发现 | 自动沉淀 |

混在一起会破坏 `index_is_stale` 基于 YAML mtime 的过期判定。

**沉淀的三道门控**（都是为了不把库喂脏）：

| 门控 | 默认 | 为什么 |
|------|------|--------|
| 等级 ≥ medium | ✅ | INFO 是「观察」不是漏洞，沉淀只会稀释召回 |
| `confirmed` 且非 `false_positive` | ✅ | 未过滤的原始命中里误报占比很高 |
| 有 `matched_at` 证据 | ✅ | 没有位置的「知识」检索时毫无用处 |

风险在**正反馈**：误报一旦入库，下次扫描会被召回，模型更倾向于把同样的东西
报成漏洞，误报越多、召回越偏。所以门控失败时宁可漏沉淀，也不冒污染风险。

未配置 LLM（没跑研判）时**自动收紧**为「必须研判过且置信度达标」——
此时所有 `confidence` 都是 0，不收紧等于把未过滤的原始命中全灌进去。

去重靠 `sha1(目标|poc_id|分类|路径)` 指纹，**不含 severity 与时间戳**，
所以同一个洞反复扫到只会更新、不会新增，库不会膨胀。

## 6. 提示工程

`llm/prompt.py` 是本项目的核心资产之一，四条设计原则：

1. **角色 + 任务 + 约束 + 格式**四段式。需要严格 JSON 输出时，
     
   模型对结构化约束的遵守率远高于散文式提问。
2. **反幻觉约束写进 system**，而不是靠祈祷。每次研判都显式声明
     
   "只能依据给出的 HTTP 证据，禁止推测未出现的信息"，并在 user 里重申。
3. **给判断标准，不给形容词。** "认真分析"没用；
     
   "401/403 只能说明路径可能存在，不能证明漏洞可利用 → needs_manual" 才有用。
4. **Few-shot 用项目里真实踩过的坑。** 软 404 误报、401 拦截页、
     
   凭据泄露这三类直接作为正负例教给模型。

降误报的判定标准写死在提示词里：

| verdict          | 判定依据                                   |
| ---------------- | -------------------------------------- |
| `false_positive` | 软 404 / 统一错误页 / WAF 拦截页 / 命中的是登录页等公共元素 |
| `needs_manual`   | 证据不足。**典型：401/403 只能说明路径可能存在**，不能证明可利用 |
| `true_positive`  | 证据明确：响应体直接输出密钥、连接串、真实 Git 配置字段         |

### YAML 结构

```yaml
id: path-env
name: 环境配置文件泄露 (.env)
category: path_probe
severity: critical
always_run: true         # 通用基线，绕过 RAG 直接执行
applies_to: [php, nodejs] # 技术栈命中时优先
tags: [disclosure, secret]

request:                 # 请求模板
  method: GET
  paths: ['.env', '.env.local']
  expect_status: [200, 401, 403]

match:                   # 匹配规则
  - patterns: ['=', 'secret']
    soft_404: ['404 not found']   # 命中即视为软 404
```

**响应头规则的 OR 语义**（容易写错，记一下）：

```yaml
match:
# 默认是 AND：两条规则必须同时成立
# 标any_of 即转为 OR——只满足一条也算命中
- op: contains
  target: header
  header: server
  value_regex: '\d+\.\d+'
  any_of: true        # Server 或 X-Powered-By 任一泄露版本号即命中
```

> 不写 `any_of` 会漏报：AND 语义要求两个头**都**有版本号，
>   
> 而只暴露 `Server` 的目标会被漏掉。

支持的 `op`：

| op         | 语义                                   | 用法                       |
| ---------- | ------------------------------------ | ------------------------ |
| `contains` | 头包含 `patterns` 任一 / 匹配 `value_regex` | 需给patterns 或 value_regex |
| `regex`    | 头匹配 `patterns` 中任一正则                 |                          |
| `missing`  | **头不存在**时命中                          | 判断"缺哪个头"                 |
| `absent`   | 头存在但不含 `value_regex`                 | 判断"缺哪个属性"                |

## 9. 降误报
这是 Web 扫描器最难的部分。三层防御：

**第一层：软 404 基线。** 绝大多数误报来自"所有路径都返回同一个页面"。
  
先探测一个随机不存在路径建立基线，之后任何与基线正文 Jaccard 相似度 ≥ 0.85
  
的命中一律丢弃。归一化时会剥掉时间戳、trace id、随机 nonce，避免同一页面
  
两次请求被判为不同内容。

**第二层：声明式规则。** `soft_404_markers` / `exclude` 字段让每条 POC
  
自己声明干扰模式。

**第三层：LLM 研判。** 拿着真实 HTTP 证据逐条判真伪，提示词里写死了
  
反幻觉约束和正负例。

最难对付的一种软 404 是**不存在的路径也返回 HTTP 200** 加统一模板页。
  
授权目标 ftitle.studio 恰好就是这样——全文所有响应一律 HTTP 200，鉴权失败
  
只体现为业务码 `{"code":401}`，状态码检查彻底失效，只有正文相似度基线能区分：

```
/.git/config            status=200  soft404=False  sim=0.0   ← 真漏洞，保留
/.env                  status=200  soft404=False  sim=0.0   ← 真漏洞，保留
/static/js/main.js.map status=200  soft404=False  sim=0.0   ← 真漏洞，保留
/nonexist              status=200  soft404=True   sim=1.0   ← 陷阱，丢弃
```

### 9.1 报告正文：为什么会出现「证据已充分」

一个真实的坑，值得记下来。

**症状**：AI 生成的报告正文只回一句「证据已充分，无需补充」，然后就没有然后了。

**根因是提示词把任务定义错了**。早先 `render_report()` 拼了一份
「测试目标 + 风险概览 + 发现清单」的骨架当user 消息，然后要求模型
「请补写三段结论」。模型收到的是一份**看起来已经写完的报告**，
于是把自己当成审稿人——审稿人当然会说「证据已充分」。

**修法**（`llm/prompt.py`）：只喂结构化素材 + 明确产出要求，
正文全部由模型生成。系统提示里显式列出五个必需章节，并写明
「禁止输出占位语 / 禁止输出元叙述」。

配套三道防线：

| 防线 | 作用 |
|------|------|
| `max_tokens` 按发现数动态放大（`1500 + 400×n`，上限 16000） | 固定 4000 在发现多时被截断，而截断是**静默**的 |
| `ask()` 检查 `finish_reason == "length"` | 以前只返回半截内容，交付出去才发现「结论章没了」 |
| `_report_ok()` 校验正文（长度/占位语/章节/发现数） | 不合格就丢弃 AI 正文，回退模板报告 |

**最重要的一条**：**发现详情段永远由模板渲染，不依赖 LLM**。
早先是`if ai_body: 用 AI 正文**替换**整个详情段`——AI 一旦失败或输出占位语，
所有命中 URL、响应片段、修复建议全部消失，只剩下概述。
这才是「报告不完整」的真正原因，比提示词问题严重得多。

`chat` 模式以前还硬传 `ai_body=""`，导致会话里按 `/report` 导出的
**一直是模板版**，与 `scan` 命令行为不一致。现在两条路径统一。

**报告结构与 PoC 展示对齐正式交付格式。** 发现详情（`## 渗透测试结果`）
按每条漏洞 `4.X [等级] 名称` 组织，固定三个子节：`漏洞描述`（编号/命中/研判/说明）→
`PoC` → `安全建议`。PoC 段是 **Burp Suite 式报文**（`>>> 请求:` / `<<< 响应:`）。

**请求与响应的待遇不一样，这是有意的**：

| | 报告内展示 | 为什么 |
|---|---|---|
| **请求（发送包）** | **完整**——请求行 + 全部请求头 + 请求体，一字不差 | 复现靠的就是它。少一个 Cookie 或路径参数，粘到 Repeater 就是**另一个请求**，等于没给出可复现的东西 |
| **响应（回包）** | **大概内容**——状态行 + 响应头 + 正文前 6000 字符 | 完整响应可能几百 KB（文件下载 / JSON 导出），全贴进来报告就没法看了；判断漏洞成立看的是「请求 + 命中了什么特征」，不是响应全文 |

请求另有 64KB 的**防爆上限**（请求是我们自己构造的，正常远小于此，只有 multipart
上传可能接近）；响应体在证据文件里的**保留**上限同样是 64KB（防 SSRF 拉回超大文件撑爆内存）。

支撑它们的是**命中落盘**：`make_finding` 时把完整报文写到
`<output_dir>/evidence/<状态码>_<哈希>.http` 并回填 `Evidence.artifact`
（报告渲染时 artifact 文件优先，字段重建兜底，截断如实标注；
`scan.evidence_dir: off` 或 `POCS_EVIDENCE_DIR=off` 可关闭）。
**完整报文永远在证据文件里**，报告只负责指路。

**「报告内容不完整」的三个根因与对策。** 用户反馈「报告输出的内容并没有达到预期，
没能输出需要的完整内容」时，实际是三个独立问题叠在一起：

| 症状 | 根因 | 对策 |
|------|------|------|
| 说明被砍到 500 字符、复现步骤丢失 | `record_finding` **登记那一刻**就做了 `description[:500]` / `matched_pattern[:400]` / `body_excerpt[:800]` 硬截断，模型写的研判根本进不了库 | 入库即完整保留；payload / response 走 `core/rawmsg.py` 结构化（请求行·头·状态·正文各归各位） |
| `<<< 响应:` 下面是一段中文分析 | 旧版把说明同时塞进 `body_excerpt`——**把分析文字摆在响应位置比留空更糟，它看起来像证据** | 渲染端 `looks_like_analysis()` 判出假响应体并剔除；回填端直接换成历史里的真响应 |
| 那条发现只有请求、没有响应 | 模型验证完没把响应交给登记工具；而响应数据**在快照里已经丢了** | `record_finding` 缺响应时自动附最近一次同 URL 的真实响应；仍没有就如实写「没有原始响应报文」。**老会话用 `/resume`（自动回填）或 `/backfill` 从对话历史里把当时的真报文补回来**，重导即生效，不必重跑扫描 |

回填有两条纪律：**只补不覆盖**（已有字段一律不动），**只按 URL 精确匹配**
（主机 + 路径 + 排序后的 query）。第二条是踩出来的——早期版本做了"忽略 query 的
同路径匹配"，结果 `/download?file=../proc/self/environ` 被挂上
`?file=../etc/passwd` 的响应，报告里的 PoC 就成了**伪造证据**。宁少不错。

> 回填复现的真实数据：`lab-l4web5.rzsec.cn` 的老会话 34 条手工发现，
> 历史里 15 次真实请求，补上 17 条（其余 URL 在历史里确实没有，如实标注缺响应）。
> 顺带修掉一个反过来的 bug：解析工具结果时只看标记行里有没有"截断"两个字，
> 而旧版 `_h_http_request` **无论切没切都写**「正文（截断 N 字符）」——
> 15 条**完整**响应全被标成"预览截断版"。判据已改成比对声明字节数与实际长度。

### 10.1 AI Agent 模式实测（本地靶场）

Agent 化改造后，用同一个靶场（`127.0.0.1:8899`）跑一轮"先做信息收集"，
  
8 次工具调用全部 `ok`，模型自主编排出的顺序是：

```
set_target → recon_fingerprint → http_request → recon_openapi
           → recon_js → recon_paths → http_request(/actuator/env) → http_request(/admin/)
```

它拿到的真实证据：13 项资产（5 接口 / 5 处硬编码凭据 / 3 个内网地址）、
  
`/actuator/env` 未授权 200 且泄露 JDBC 连接串、`/admin/` 返回 401。

**反幻觉约束真实生效**——模型没有把JS 里的凭据直接报成"高危泄露"，而是逐条标注可信度：

> `AKIAIOSFODNN7EXAMPLE` 是 AWS 官方文档的示例值，**大概率是假货**；
>   
> JWT 签名段是占位符，**假**；`sk-live-…` / `Sup3rS3cret!` **需验证是否真能用**。
>   
> `/actuator/env` 未授权可访问是**已确认**的（有真实 200 + JSON 响应）。

模型还主动指出指纹矛盾：`Server` 头同时有 `BaseHTTP/0.6 Python` 和 `Apache/2.4.62`，
  
判定真实运行时是 Python 而页面文案在伪装 Spring Boot —— 这正是固定剧本做不出来的判断。

> 一次实测踩坑：靶场进程被`nohup ... &` 意外回收后，外部工具 curl 全部返回
>   
> 502（代理转发到已死进程），模型被这个假象带偏，把 4 次调用浪费在反复复测上，
>   
> 8 步预算耗尽。**排查工具结果异常时，先确认目标进程是否还活着**——
>   
> 502/超时这类网络层错误往往不是工具或授权的问题。

## 12. 配置

优先级 **环境变量 > .env > config.yaml > 默认值**。
  
`.env` 由启动时自动读取，且**不覆盖已存在的环境变量**——
  
CI 里`export DEEPSEEK_API_KEY=...` 注入的密钥必须优先于本地文件，
  
否则本地一个过期 Key 会静默盖掉流水线的正确配置。

**`POCS_*` 的三条统一规则**（`scripts/config_test.py` 守着）：

1. **空字符串 = 未设置** → 保留 `config.yaml` 的值。
   早期 `POCS_READONLY=""` 会把只读**关掉**（危险方向），
   而 `POCS_PORT_SCAN=""` 什么都不做——同类参数两种行为，只能靠猜。
2. **类型写错 → 保留默认 + stderr 一行警告**，不再崩溃。
   `POCS_TIMEOUT=abc` 以前直接 `ValueError` 给你满屏 traceback。
3. `POCS_QUIET_CONFIG=1` 可关掉这些警告。

`config.yaml` 里的非法值同理：加载期就被拦住，**坏项保留默认、同段好项照常生效**，
拼错的字段名会被点名（以前 `top_k: "abc"` 会静默变成字符串，
一路跑到检索器里 `max(top_k, 10)` 才 TypeError，报错点离根因隔了半个程序）。

> `init` 生成的 `.env.example` 里 `api_key` 一律留空占位。Key 只落`.env`，
>   
> **不要写进 `config.yaml`** —— 那个文件是要提交进仓库的。

### 模型选择

官方取值只有两个（依据 [api-docs.deepseek.com](https://api-docs.deepseek.com/zh-cn/)）：

| 模型名               | 特点   | 默认用于               |
| ----------------- | ---- | ------------------ |
| `deepseek-flash`  | 快、便宜 | 高频机械任务：RAG 重排、误报研判 |
| `deepseek-v4-pro` | 强、贵  | 低频理解任务：业务建模、报告撰写   |

默认全部走 `deepseek-flash`。想给建模/报告用强模型：

```bash
python flower_pow.py chat https://target.com --deep-model deepseek-v4-pro
python flower_pow.py scan https://target.com --model deepseek-v4-pro   # 整体换
python flower_pow.py models                                            # 查看清单
```

> ⚠ **注册表以外的名字会被原样发给服务端**。厂商对已下线的模型名不报错，
>   
> 只会静默换成别的模型提供服务——所以程序在启动时、`engines`、`models` 三处
>   
> 都会打印警告。看到警告就说明该改配置了。
>
> 本项目**不维护下线模型名清单**：那是历史包袱，且永远补不全（厂商每改一次
>   
> 名就要加一条）。所以改成"注册表里没有的名字一律放行但必报警告"，警告里
>   
> 直接点明"可能是已下线的旧名"。
>
> 模型名只在 `llm/models.py` 的注册表里定义。改名或加新模型改那一个文件，
>   
> `config.yaml` / `init` 模板 / CLI 全都会跟着变。
>
> 第三方模型（OpenAI、vLLM、自建网关）填任意名字都能跑，但会被标记为
>   
> "未在注册表中"并**关闭 `thinking` 参数**——那是 DeepSeek 扩展字段，
>   
> 发给不支持的网关可能直接 400。

## 13. 安全设计

- **只读优先**：`readonly: true` 时所有 `intrusive` POC 被跳过，
    
  攻击性外部工具（sqlmap / nikto / hydra / masscan）直接拒绝执行。
- **无目标范围限制**：工具**不做授权白名单校验**，可以指向任意目标。
    
  使用者需自行确保测试已获授权——这是本工具的设计取舍。
- **证据留存**：每条发现带完整 `Evidence`（请求行、状态、响应头、body 截断、耗时），
    
  `--save-evidence` 可把原始报文落盘到 `output/evidence/` 直接复制到 Burp 复现。
- **密钥不进报告**：只从环境变量 / `.env` 读取，`.gitignore` 已排除 `.env`；
    
  **不写 config.yaml**（那是要提交的）。终端回显一律脱敏。
- **只扫描能连通的目标**：端口扫描只做 TCP connect，不扫 UDP、不做漏洞探测。
- **写操作逐条人工审核**：任意文件上传已从「只读禁区」改为开放，但**每次发起前都要
  人工确认一次**（审核文案写明目标 URL、文件名、以及"会留下文件需手工清理"）。
  没有审核通道时（非交互环境、CI）一个上传请求都不会发。开关：
  `scan.file_upload_probe_enabled` / `scan.upload_require_approval`。
- **一键全自动有警告门**：`/auto` 或 `Alt+Shift` 会先把完整后果（含"上传不再逐条询问"）
  打出来，确认后才跑。全自动期间的放行**每一条都打印并写进 notes**——
  "一键"不等于"无法审计"。

**Agent 模式的执行层约束**（模型不可绕过，见 §4.1）：

| 闸门         | 拦截什么                                    |
| ---------- | --------------------------------------- |
| 外部工具参数白名单  | 未声明的选项、越界文件路径（必须在项目目录内且存在）              |
| 只读拦截       | `intrusive` 工具在只读模式下直接拒绝                |
| 无 shell 执行 | 一律 argv 数组 + `shell=False`，无重定向/管道/命令替换 |
| 循环死锁检测     | 目标不可达时模型的无限重试 —— 同一调用重复 3 次即注入收尾指令         |

报告头部仍会输出合规声明（`output/report/`），提示确认测试范围。
